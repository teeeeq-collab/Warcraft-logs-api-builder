## Implemented vs planned

**Implemented:** auth, GraphQL client, rate limiting, retry/backoff, raw cache,
pagination, schema introspection, report discovery, normalization, SQLite
persistence + migrations, pull assignment, duplicate detection, coverage
manifest, validation reporting, stream benchmarking, pack identity indexing,
database partitioning by file.

**Planned / absent:** analytical engine, query layer, export formats beyond two
report files, cohort matching, similarity search, state reconstruction, compact
event representation, LLM interface of any kind.

## Summary statement

> **If development stopped today, the system could** collect Mythic+ runs from
> Warcraft Logs losslessly and resumably, store them in a versioned SQLite
> schema with full provenance, assign events to pulls, detect probable duplicate
> uploads, measure its own API cost, and produce a validation report that states
> what it could not establish — **but could not yet** answer any analytical
> question about the corpus, export data in any machine-consumable format beyond
> two fixed reports, or expose anything to an LLM or external caller other than
> through raw SQL against the database file.

# PART 3 — CURRENT EXECUTION FLOW

Traced end-to-end for `wclmplus collect --report-list reports.txt` **[CODE]**.

```text
cli.py::collect                          argument parsing (Typer)
 → cli.py::_load_settings                Settings + .env, registers secrets for redaction
 → cli.py::_load_config                  ProjectConfig.load(): dungeons/sampling/roles/hotfix YAML
 → cli.py::_database(settings, path=…)   Database() → migrate() → schema version check
 → cli.py::_client                       GraphQLClient(settings)
 → reportsource.ManualReportSource.from_file   report codes + ReportProvenance
 → Collector.collect(candidates, event_profile=…, focus_player=…)
     ├─ Collector.start_job              collection_jobs row; config_hash, git commit, versions
     ├─ client.fetch_rate_limit          opening point-budget reading (uncached)
     └─ per candidate: Collector.collect_report
         ├─ upsert report_provenance
         ├─ query report_metadata        → normalize.normalize_report → reports row
         ├─ Collector.fetch_fights       → normalize.is_mythic_plus filters to M+ runs
         └─ per fight: Collector._collect_run
             ├─ normalize.run_id_for     ID = "<report_code>:<fight_id>"
             ├─ normalize.normalize_run  timestamps, keystone fields, key_bracket, hotfix_epoch
             ├─ carry forward duplicate_group_id / is_canonical from any prior row
             ├─ upsert dungeon_runs
             ├─ Collector._store_master_data  → normalize_actors (players pseudonymized),
             │                                   normalize_abilities
             ├─ Collector._store_roster       → normalize_run_players (class/spec/role/ilvl)
             ├─ Collector._collect_pulls      → normalize_pulls → pulls + pull_npcs,
             │                                   composition_signature, species_signature,
             │                                   instance_count + confidence
             ├─ PullAssigner.from_rows        closed intervals [start, end]
             ├─ Collector._resolve_focus_actor  (see Part 9 — currently cannot match)
             └─ per EventRequest (from event_requests(profile, focus_actor_id)):
                 ├─ Collector._resume_point       last ok page → cursor + next index
                 ├─ EventPaginator                loop guards, boundary matching
                 │   └─ client.execute(report_events)   cache → rate limiter → HTTP → retry
                 ├─ PullAssigner.assign           event → pull_id, records unassigned bucket
                 ├─ normalize.normalize_event     row + `extra` JSON for unpromoted fields
                 ├─ one transaction: event_pages row + DELETE its events + INSERT events
                 └─ Collector._record_coverage    run_stream_coverage row (always, incl. failure)
     ├─ Collector._record_api_cost       api_cost diagnostic (points delta, requests, runs)
     └─ Collector.finish_job             collection_jobs closed out
 → cli prints summary, database path, next command
```

## Stage responsibilities

| Concern | Where | Notes |
| --- | --- | --- |
| Run IDs generated | `normalize.run_id_for` | `"<report_code>:<fight_id>"` — report-local, globally unique because report codes are |
| Pull IDs generated | `normalize.pull_id_for` | `"<run_id>:<wcl_pull_id>"` |
| Player IDs generated | `sanitize.identity_hash` | salted SHA-256 of lowercased character name, 12 hex chars |
| Timestamps normalized | `normalize.normalize_event` | four bases stored: `rel_ms`, `abs_ms`, `run_rel_ms`, `pull_rel_ms` |
| Source/target actors resolved | not resolved at ingest | raw numeric `sourceID`/`targetID` stored; `actors` table joined at query time |
| NPC instances resolved | `normalize.instance_count` | from `minimumInstanceID`/`maximumInstanceID` range, with confidence |
| Pulls assigned | `pullassign.PullAssigner.assign` | called per event during collection |
| Failures recorded | `db.diagnostic` → `ingest_diagnostics`; `run_stream_coverage.status` | |
| Completeness checked | `Collector._record_coverage` | `status='ok'` only when the last page has no forward cursor |
| Quota tracked | `ratelimit.RateLimiter`; `Collector._record_api_cost` | budget read at both job boundaries |
| Raw responses cached | `rawcache.RawCache` via `client.execute` | gzipped JSON, secret-scanned before write |

## Known stream issues **[DATA]**

- `hostilityType` **defaults to Friendlies on every stream tested** (Casts, Buffs, DamageDone, Healing, Threat). Unfiltered never means "both".
- `Resources@Enemies` returned **0 events across 10 fights, all exhausted** — NPC energy is not exposed.

- `CombatantInfo` **ignores hostility** — all three requests returned byte-identical results on 9 of 10 fights.
- `DamageDone` and `Healing` unsplit requests return only the friendly side.

# PART 7 — EXACT STORAGE ARCHITECTURE

## Formats present

| Format | Used for | Status |
| --- | --- | --- |
| **SQLite** | The single canonical store | ✔ **[CODE][DATA]** |
| **gzipped JSON** | Raw API response cache | ✔ **[CODE]** |
| **JSON** | `validation.json`, `stream_benchmark.json`, `recon_findings.json` | ✔ report artifacts only |
| **Markdown** | `VALIDATION_REPORT.md`, `STREAM_BENCHMARK.md` | ✔ human-facing |
| DuckDB / Parquet / CSV / JSONL | — | **absent [CODE]** |

Default database: `data/db/wclmplus.sqlite`. `--database <name>` resolves a bare
name inside `data/db/`; an explicit path is used as given **[CODE][TESTS]**.

`PRAGMA foreign_keys = ON` and WAL journaling are set on every connection
**[CODE]**. There is **no compression and no partitioning inside a database** —
partitioning is by separate file only **[CODE]**.

## Schema relationships

```text
collection_jobs ──────┐
report_provenance ─┐  │
                   ↓  ↓
                reports
                   ↓
              dungeon_runs ──→ run_players ──→ players
               ↓    ↓    ↓
               │    │    └──→ run_stream_coverage
               │    └──→ pulls ──→ pull_npcs
               │            ↑
               ↓            │ (pull_id)
           event_pages ──→ events
                             │
        actors ←─────────────┤ (report_code + source_id, join-time only)
     abilities ←─────────────┘ (ability_game_id, join-time only)

        ingest_diagnostics (run_id / job_id, nullable)
```

15 tables at schema 3. Key constraints **[CODE]**:

- `events` identity: `UNIQUE (page_id, seq_in_page)`
- `event_pages`: `UNIQUE (run_id, data_type, IFNULL(hostility,''), page_index)`
- `dungeon_runs`: `UNIQUE (report_code, fight_id)`
- `run_stream_coverage`: unique on run + stream + hostility + source/target
- `pull_npcs`: unique on pull + npc_game_id + actor_id
- FKs from events → event_pages, dungeon_runs; pulls → dungeon_runs; etc.

**No foreign key exists from `events` to `actors` or `abilities`** — those are
join-time lookups on `(report_code, source_id)` and `ability_game_id` **[CODE]**.

24 indexes in 001, 4 in 002, 3 in 003. `events` is indexed on
`(pull_id, rel_ms)`, `(run_id, rel_ms)`, `(ability_game_id, type)`,
`(run_id, source_id, source_instance, rel_ms)`, target, and type **[CODE]**.

### FINDING — `--focus-player` cannot currently match any player

## Cross-run pack identity — **EXISTS**

This is the direct answer to the question in the request. The project **does**
have a cross-run concept of "this pull in run A is essentially the same pull as
that pull in run B", implemented as two complementary signatures **[CODE]**:

- `species_signature` — identity that survives *how* the pull was made. Same
  trash group pulled with three or five of something yields one signature.
- `composition_signature` — exact, counts included. The **difference between the
  two is the oversized-pull signal.**

Both are indexed (`idx_pulls_species` on `(dungeon_key, species_signature)`,
`idx_pulls_signature` on `composition_signature`). The `packs` command exposes
them **[CODE]**.

**Caveat:** `species_signature` and `dungeon_key` were added at schema 3 /
normalizer 2. Runs collected earlier carry NULL in both until re-collected
**[CODE]**. The 94-run corpus was re-collected under normalizer 2 **[DATA]**.

There is **no named pull archetype, no clustering, and no similarity metric** —
identity is exact signature equality only **[CODE]**.

## Event assignment

- `PullAssigner` uses **closed** intervals `[start, end]`, bisect + backward scan **[CODE]**
- Overlapping pulls detected and recorded as `overlapping_pulls` diagnostics — **2 observed** **[DATA]**
- Unassigned events retain `pull_id = NULL` and `pull_rel_ms = NULL`, bucketed as before-first / between / after-last **[CODE]**
- **Current assignment rate: 97.83%; 108,124 events unassigned** **[DATA]**

Known failure cases: events outside every pull (boss intros, between-pull
movement, trash outside recorded pulls), and overlapping pull intervals where
the first match wins **[CODE][DATA]**.

# PART 14 — RAW RESPONSE PRESERVATION

**Raw responses are preserved.** `rawcache.RawCache` **[CODE]**:

| Property | Value |
| --- | --- |
| Location | `data/raw_cache/`, sharded by report code |
| Format | gzipped JSON envelope, `<key>.json.gz` |
| Envelope | response + redacted request params + provenance + `fetched_at` |
| Key | SHA of report code + query kind + canonical params + `QUERY_VERSION` |
| Deduplication | identical requests collapse to one file |
| Secret safety | serialized bytes scanned before write; a hit raises `CacheSecurityError` rather than writing |
| Audit | `cache-audit` rescans the whole cache and exits non-zero on a hit |
| `Authorization` headers | never passed in; stripped defensively via `_FORBIDDEN_PARAM_KEYS` |

`events.raw_cache_path` on `event_pages` links a stored page back to its cache
file **[CODE]**.

## Replay capability

Because `client.execute` consults the cache first, **re-running collection with
a changed normalizer rebuilds the database from local files without spending API
quota**, provided `QUERY_VERSION` is unchanged **[CODE][INFER]**. There is **no
explicit "rebuild from cache" command** — replay is a side effect of the cache
being consulted, and would require deleting the events and re-running `collect`
**[CODE]**.

**Caveat [INFER]:** bumping `QUERY_VERSION` (as happened at 4→5) changes cache
identity, so pages cached under an older query version will not be served to a
newer one and would be re-fetched.

**Cache size on the live machine: [UNKNOWN]** — `cache-stats` has not been run
in a session visible to this audit.

## Is the logic reusable from Python without the CLI?

**Yes, for collection.** This works today **[CODE][TESTS]** — it is exactly what
the test suite does:

```python
from wcl_mplus.client import GraphQLClient
from wcl_mplus.collect import Collector
from wcl_mplus.configs import ProjectConfig
from wcl_mplus.db import Database

collector = Collector(GraphQLClient(settings), Database(path), ProjectConfig.load())
result = collector.collect(candidates, event_profile="mechanics")
```

**Yes, for validation and dedupe:** `collect_validation(db)`,
`group_duplicates(db)`, `paired_abilities(db)` all take a `Database` and return
plain data **[CODE]**.

**No, for querying.** There is no `repository.get_pull(...)` equivalent. Every
read is an ad-hoc SQL string at its call site **[CODE]**.

# PART 22 — LARGE-CORPUS SCALABILITY

Extrapolated from measured 23.2 MB and 52,912 events per run **[DATA]**;
projections are **[INFER]**.

| Scale | Size | Events | Assessment |
| --- | ---: | ---: | --- |
| 1,000 runs | ~23 GB | ~53M | **Fine.** Indexed lookups unaffected; aggregates seconds to a minute |
| 10,000 runs | ~232 GB | ~530M | **Workable, uncomfortable.** Index size grows; full scans become minutes. Backup/VACUUM an overnight job |
| 100,000 runs | ~2.3 TB | ~5.3B | **Current design would fight this.** Single-file SQLite, no columnar storage, no partition pruning inside a file |
| >1 TB | — | — | **Not viable as one file** |

## Where the current implementation is fine

- **Incremental collection**: excellent. Page-level resume, idempotent re-ingest, completed streams skipped **[CODE][TESTS]**
- **Schema evolution**: numbered migrations with gap detection and a version gate **[CODE][TESTS]**
- **Write amplification**: low — batched `executemany`, one transaction per page **[CODE]**
- **Indexes**: the six on `events` cover the obvious access paths **[CODE]**

## Where it becomes problematic

| Concern | Detail |
| --- | --- |
| **Row-oriented storage** | An analyst scanning one column of 5B rows reads all 41. Columnar (Parquet/DuckDB) is the natural fit and is absent |
| **No intra-file partitioning** | Only file-level, via `--database`. Nothing prevents mixing seasons in one file except discipline |
| **`extra` JSON** | Unindexed and re-parsed per row; grows with every unpromoted field |
| **String repetition** | `events.buffs` stores a delimited aura string per row — see Part 23 |
| **RAM** | SQLite is fine with a small page cache, but any `GROUP BY` over hundreds of millions of rows spills |
| **Backup** | One 2.3 TB file; no incremental backup story |
| **VACUUM** | Rewrites the entire file |

5. **`Resources@Enemies` returns nothing.** Zero events across 10 fights, all exhausted. NPC energy is not exposed. **[DATA]**
6. **`Threat` contains no threat value.** It returns casts/deaths/applydebuffs with `melee`/`fake`/`feign` flags. It cannot answer "who had aggro". **[DATA]**
7. **`CombatantInfo` ignores hostility.** Splitting it collects the same rows twice. **[DATA]**
8. **Raw API payloads ARE retained** — gzipped, secret-scanned, and linked from `event_pages.raw_cache_path`. Normalization is re-runnable offline. **[CODE]**
9. **Nothing is discarded at normalization.** Unpromoted fields go to `events.extra`. **[CODE]**
10. **SQLite is the only canonical store.** No DuckDB, no Parquet, no CSV, no JSONL. **[CODE]**
11. **There is no export.** Two report files and console output. No event-level export in any format. **[CODE]**
12. **There is no analytical engine and no query layer.** `validate.py` is a validation reporter, not analysis. **[CODE]**
13. **Pull IDs are report-local** (`"<report_code>:<fight_id>:<wcl_pull_id>"`), and **NPC actor IDs are report-local**. Only ability IDs, NPC game IDs and player hashes are global. **[CODE]**
14. **Cross-log pack identity DOES exist** — two signatures, both indexed. Do not assume it needs building. **[CODE]**
15. **The corpus has never been deduplicated.** `analysable = 94` overcounts. **[DATA]**
16. **Collection is strictly serial.** No concurrency anywhere. **[CODE]**
17. **Quota is not the bottleneck** — 13.19 points/run measured, against a 3,600/hour budget. Earlier statements that quota binds first were based on an estimate the measurement disproved. **[DATA]**
18. **Most root documentation is stale** (dated 2026-09-12, before schema 2 and 3). `API_NOTES.md` is the exception and is canonical for live API behaviour. **[CODE]**
19. **`events` has no foreign key to `actors` or `abilities`.** Those are join-time lookups. **[CODE]**
20. **14,568 enemy casts have NULL `sourceInstance`** and it is deliberately never defaulted to 1. **[DATA]**
21. **Five ability pairs are 1:1 inseparable** — summing casts across abilities double-counts. **[DATA]**
22. **`--database` partitions by file only.** Nothing prevents mixing seasons in one file except operator discipline. **[CODE]**

| --- | --- | --- | --- | --- | --- |
| 1 | **`--focus-player` silently non-functional** | **CRITICAL** | The one mechanism designed to make a large reference corpus affordable collects nothing, and fails silently | **Yes** — one query change, plus a test | **Yes** — any corpus built expecting focus data is worthless for that purpose |

# PART 39 — WHAT SHOULD NOT BE REWRITTEN

| Component | Why keep it |
| --- | --- |
| **`rawcache.py`** | Lossless, gzipped, secret-scanned, auditable, and it makes normalization re-runnable without spending quota. This is the safety net that makes every other decision reversible. |
| **`normalize.py`** | Pure functions, no I/O, lossless by construction (`extra` catch-all). Easy to test, easy to re-run, easy to extend. |
| **`paginate.py`** | Correct under both inclusive and exclusive cursor semantics, with loop guards and multiset boundary matching. Live-validated at 316 pages with zero repeats. This was hard-won. |
| **`run_stream_coverage` (migration 002)** | The distinction between "asked, none" and "never asked" cannot be reconstructed later. Any future analytical layer depends on it. |
| **Provenance chain** | Event → page → raw cache file → job → git commit. Unbroken. Rare, and expensive to retrofit. |
| **`db.py` migration runner** | Numbered, gap-detecting, version-gated, idempotent. Works. |
| **`redaction.py` + secret handling** | Registry, log filter, exception scrubbing, cache write guard, audit command. Security done once, done properly. |
| **The validation report's honesty discipline** | Limitations reported next to results; zeros distinguished from gaps; capped measurements labelled as lower bounds. This culture is worth more than any single feature. |
| **Config-driven profiles** | Adding a stream or profile is a YAML edit. The extension mechanism already works. |
| **The offline test suite + simulator** | 361 tests, no network, no recorded fixtures. It caught real bugs repeatedly. |

# PART 40 — OPEN QUESTIONS

Questions that **cannot** be answered by inspecting this repository.

1. **Hotfix epoch boundaries.** Real Blizzard patch/hotfix dates for Midnight Season 2. The project refuses to invent them; the file is ready.
2. **Does `talentTree` / `customPowerSet` encode hero talents?** Observed in CombatantInfo but semantics unverified against the game.
3. **Do threat values exist on another WCL endpoint?** The events `Threat` stream carries none; `table`/`rankings` endpoints are untested.
4. **What is the raw cache size on the owner's machine?** Determines whether cache-backed replay is practical at scale.
5. **Is `sourceInstance` ever recoverable** for the 14,568 affected events — e.g. by correlating with `DamageDone` from the same NPC at the same timestamp?
6. **What is the true events-per-run for `DamageDone`?** Two of ten probes were still capped at 120,242 after 60 pages.
7. **Which dungeons and specs are actually in the 94-run corpus?** Stored but never reported.
8. **What defines a "high-performing" cohort?** No metric exists; this is a research-design question, not an engineering one.
9. **Is the WCL API's `hostilityType` default documented anywhere**, or is the observed Friendlies-default an undocumented behaviour that could change?
10. **What is the intended retention policy?** Whether the raw cache is kept forever changes the storage projection materially.
11. **Will multiple machines share a corpus?** Determines whether `IDENTITY_SALT` must become a configured, version-controlled constant.
12. **Does the owner intend to distribute databases?** Player pseudonyms are name-hashes and are reversible by dictionary attack for common names.
